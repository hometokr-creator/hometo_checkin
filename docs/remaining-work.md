## 개발 순서와 완료 조건

### 1. 고객·계약 연결 설계와 시트 동기화

- [x] `checkin_guest.guest_id` ↔ 내부 UUID의 유일한 매핑과 중복 ID 차단 구현. ID 변경 시 기존 고객은 보류하고 새 ID와 자동 병합하지 않음.
- [x] 미완성 신규 고객은 DB에 저장하지 않음. 기존 저장 고객의 필수정보 누락은 유효 값과 이력을 보존하고 보류.
- [ ] 재계약·기간 정정·중도 퇴실을 구분하고 과거 회차의 계약 맥락을 보존하는 구조를 정한다. 고객과 계약 테이블 분리는 아직 확정된 구현 방식이 아니다.
- [ ] Google Sheets 서버 인증 방식과 시트 읽기 권한을 설정한다. 코덱스 커넥터로 읽을 수 있다는 사실이 앱 서버의 자동 동기화 권한을 의미하지는 않는다.
- [x] 대상 탭 읽기 및 미리보기/저장 명령 연결. 연결 도구로 읽은 실제 시트로 최초 저장 검증.
- [x] 특이사항 범주·상세, 고객상태, 외부 ID와 필요한 고객정보의 DB 저장 구현.
- [x] 빈 셀·행 삭제·ID 변경의 보류 정책, 일일 주기, 재실행 중복 방지 구현. 빈 전체 결과는 기존 고객을 유지하고 실패 처리.
- [x] DB 실행 기록에 최근 시각·결과 건수·오류 코드 저장. 일반 로그에서 원문 개인정보/인증키 제외. 운영 화면에서 기록을 보여주는 UI는 후속 작업.

완료 조건: 가상 시트 데이터로 신규/수정/중복/빈값/삭제 후보를 검증하고, 같은 입력을 다시 처리해도 고객이 중복 생성되지 않는다. 실제 시트 쓰기 및 실고객 DB 입력은 범위를 확인한 뒤 진행한다.

### 2. 운영 화면의 실제 고객정보 연결

- [ ] 기존 응답 상세의 참여자 정보에 확정된 8개 고객정보를 연결한다.
- [ ] 연락처 등 고객정보를 인증된 운영자에게만 반환하고 입주자 API 응답에 포함하지 않는다.
- [ ] 고객별 과거 응답 연결이 동명이인·연락처 변경·재계약에도 유지되는지 검증한다.
- [ ] 테스트 운영자의 실제 이메일 로그인, 응답 목록·상세·확인/해제 저장을 검증한다. 공유 프로젝트의 기존 Auth 설정에 영향을 주지 않는 연결 방법을 먼저 확인한다.

완료 조건: 가상 고객의 실제 브라우저 제출 결과를 로그인한 운영자가 고객정보·특이사항·과거 응답과 함께 확인할 수 있다.

### 4. 알림톡 업체 준비와 API 연결

업체 계약/채널·템플릿 준비는 1~3단계 개발과 병행할 수 있다.

- [x] 사용자: NHN Cloud 알림톡 계약 완료.
- [ ] 사용자: NHN Cloud 발신프로필/카카오 채널 등록·인증 완료.
- [ ] 사용자와 함께: 회차별 문구·버튼 링크·변수 구성, 업체 템플릿 등록/승인 상태 확인.
- [ ] 개발: 업체 API 인증, 템플릿 코드, 발송 요청·결과 조회 또는 콜백 연결.
- [ ] 발송 전에 고객·계약·회차 세션과 토큰 링크를 연결한다. URL 클릭마다 새로운 응답 기회를 만들지 않는다.
- [ ] `checkin_delivery`에 요청·성공·실패·공급자 메시지 ID를 기록한다. 요청 접수와 실제 전달 결과를 구분한다.
- [ ] 타임아웃·응답 유실·중복 콜백·실패 재시도 정책을 구현하고 토큰·응답 만료 기준을 실제 발송 흐름에 맞춘다.
- [ ] 미응답 리마인더 시점·횟수·중지 조건과 원래 응답 마감 유지 여부를 확정한다.
- [ ] 테스트는 모의 발송을 기본으로 한다. 실제 발송 검증은 사용자가 지정·승인한 테스트 번호에 한정한다.

완료 조건: 모의 결과 및 승인된 테스트 번호로 발송→링크 진입→제출→운영 조회를 검증하고, 실패/중복/재시도 시 원치 않는 추가 발송이 없다.

### 5. 운영 연결 및 출시 전 검증

- [ ] 실제 발송 전 고객상태까지 확인하고 발송 보류 대상을 확정한다. 고객 저장 조건을 통과한 5명도 자동 발송 승인 대상은 아니다.
- [ ] 운영 DB의 기존 가상 고객·응답·토큰 정리 범위를 확인하고 필요한 백업 후 승인된 대상만 정리한다.
- [x] 검증한 고객 동기화·일정 관련 SQL을 운영 DB에 적용하고 실제 고객 데이터를 연결한다. 현재 5명은 상태 조건 미충족으로 일정 생성 보류.
- [ ] 운영/테스트 환경변수와 인증키·접근 비밀값을 분리한다. 현재 `.env.local`은 운영 프로젝트를 가리키며, 테스트는 전용 명령을 사용한다.
- [ ] Vercel Preview를 테스트 DB에, 운영 배포를 운영 DB에 연결한다. 기존 Preview는 과거 설정상 현재 운영 지정 프로젝트에 연결돼 있으므로 전환 전 실고객 테스트에 사용하지 않는다.
- [ ] 배포 기준 GitHub 저장소를 확인한다. 기존 문서의 로컬 origin/연결 저장소 차이를 해소한 뒤 배포 경로를 확정한다.
- [ ] 운영자 Auth 사용자·allowlist·매직링크 리다이렉트·이메일 발송 설정과 실제 로그인/로그아웃을 확인한다.
- [ ] 프록시·배포 접근 로그의 토큰 마스킹 및 인증키 비노출을 확인한다.
- [ ] iOS·Android 카카오 인앱에서 키보드·하단 버튼·스크롤·새로고침·중복 제출·만료 링크를 검증한다.
- [ ] 첫 발송 대상을 검토하고 소규모 발송 후 수신·완료·실패를 확인한다. 스케줄러 중지 및 실패 확인 방법을 운영 문서에 기록한다.

완료 조건: 운영자가 실고객의 응답을 정확한 고객·회차와 함께 조회할 수 있고, 발송 중지·실패 대응 방법이 준비된 상태에서 운영을 시작한다.

## 작업 경계 및 참고

- 작업 전 및 수정·커밋 직전에 브랜치/변경사항을 확인한다. AD 작업은 `feat/checkin-admin`, 새 시트 연동 작업은 `codex/guest-sheet-sync`에서 진행하며 `main`은 읽기 전용이다.
- 요청 범위 내 검증된 변경은 커밋할 수 있다. 푸시·PR·병합·배포는 별도 요청/기존 명시적 승인 범위에서만 수행한다.
- 이 목록은 운영 데이터 삭제·실제 메시지 발송·배포를 일괄 승인하는 문서가 아니다.
- 테스트 프로젝트는 다른 서비스와 공유한다. DB 전체 초기화, 다른 기능 테이블/Storage 삭제, 공유 Auth 템플릿의 임의 변경을 하지 않는다.
- 초기 출시 범위에 통계 추가 개발, 집주인 설문, 실제 커뮤니티, 운영자 긴급 알림을 추가하지 않는다. 기존 보류 정책을 유지한다.
