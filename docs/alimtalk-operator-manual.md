# 홈투게더 정기 체크인 알림톡 관리자 설명서

작성 기준: 2026-09-19 · 코드 기준: `codex/contract-checkin-schedule`, `9ed20cd`

이 문서는 알림톡 담당자가 고객정보를 반영하고, 발송 일정과 결과를 이해하고, 접수된 응답을 관리하기 위한 안내서입니다. 아래의 **현재 상태**는 사용자 확인 및 저장소 기록 기준입니다. 이번 문서 작성 중 운영 DB·NHN 콘솔·배포 설정을 새로 조회하거나 변경하지 않았습니다.

## 먼저 알아둘 현재 상태

| 구분 | 현재 상태 |
| --- | --- |
| 고객 시트 → 운영 DB 동기화 | 기존 기록상 운영 반영·Apps Script 교체·일일 동기화 확인 완료 |
| 계약별 체크인 일정 계산 | 구현 및 운영 일정 DB 적용 완료 |
| 초기 운영 일정 계산 결과 | 9월 18일 기록 기준 고객 5명 모두 고객상태 조건 미충족으로 보류, 생성 계약·일정 0건. 현재 실시간 수치는 별도 확인 필요 |
| NHN 발송 요청·결과 조회·토큰 기한 연결 | 코드 구현 및 테스트 DB 검증 완료 |
| 이번 발송 기능의 운영 DB 적용·웹 배포 | 아직 진행 전 |
| NHN 승인 확인·담당자 번호 수신 테스트 | 다음 단계 |
| 운영 자동 발송 | 아직 꺼져 있음. 자동 호출 장치 연결도 남아 있음 |
| 운영자 응답 화면 | 코드 구현 완료. 실제 운영 이메일 로그인·수신 후 응답 조회는 출시 전 검증 필요 |

**고객 동기화 자동 실행과 알림톡 자동 발송은 서로 다른 기능입니다.** 고객 동기화가 성공하거나 DB에 고객이 저장됐다고 알림톡이 바로 발송되지는 않습니다.

문서에서 사용하는 용어는 다음과 같습니다.

| 용어 | 뜻 |
| --- | --- |
| 동기화 | 고객 시트 내용을 체크인 DB에 반영하는 일 |
| 회차 | 입주 1주차·첫 달·월간·재계약 전처럼 한 번의 체크인 기회 |
| 일정 | 어느 고객의 어떤 계약에 어떤 회차를 언제 보낼지 저장한 계획 |
| 세션 | 특정 고객·계약·회차에 연결된 설문 응답 기회 |
| 토큰 | 그 세션에 접근할 수 있게 하는 비밀 링크의 무작위 문자열 |
| 접수 | NHN이 발송 요청을 받아들인 상태 |
| 전달 성공 | NHN 조회 결과에서 메시지가 전달됐다고 확인된 상태. 고객이 읽거나 답변했다는 뜻은 아님 |

## 1. 알림톡의 운영 방식

### 1-1. 전체 흐름과 관리 장소

```text
고객 원본 시트: 게스트_마스터
    ↓ 매일 아침 동기화 또는 담당자의 syncGuests 실행
우리 서비스의 Supabase DB: 고객정보 검증·저장
    ↓ 저장과 함께 계약 및 체크인 일정 계산·보류
발송 예정일: 자동 호출 장치가 서버 실행 [운영 연결 예정]
    ↓ 발송 대상 재확인 → 세션·토큰 발급 → NHN 발송 요청
NHN Cloud: 승인된 템플릿으로 알림톡 전달
    ↓ 서버의 반복 결과 조회로 실제 전달 성공 반영
고객: 알림톡 버튼 → 회차별 설문 → 제출
    ↓
관리자 페이지: 응답·불만·긴급·과거 이력 확인
```

| 할 일 | 사용하는 곳 |
| --- | --- |
| 고객 이름·전화번호·상태·계약 날짜 수정 | Google 시트 `게스트_마스터` |
| 지금 DB 반영, 일일 동기화 설정 | 원본 시트에 연결된 Google Apps Script |
| 알림톡 템플릿 등록·심사·전달 결과 확인 | NHN Cloud 콘솔 |
| 고객·일정·발송 기록의 상세 진단 | 권한 있는 담당자가 Supabase DB 및 서버 실행 기록 확인 |
| 설문 결과와 불만 확인 | 홈투게더 관리자 페이지 |
| 운영 발송 활성화·자동 호출 설정 | 개발 담당자의 서버 환경 설정 및 배포 |

우리 서비스의 고객 DB와 NHN 발송 시스템은 별개입니다. NHN에 고객 시트 전체를 매일 복제하지 않습니다. 발송할 때 필요한 수신번호·템플릿 코드·이름·토큰 등을 NHN에 전달합니다.

### 1-2. 어떤 시기에 발송하나요?

기준은 시트의 **실제 계약 시작일과 실제 계약 종료일**입니다. 희망 입주일·희망 거주기간·메모에서 날짜를 추정하지 않습니다.

| 회차 | 발송 날짜 | 내부 회차 값 |
| --- | --- | --- |
| 입주 1주차 | 신규 계약 시작일 +7일 | `onboarding-d7` |
| 첫 달 | 신규 계약 시작일 +1개월 | `monthly-first` |
| 월간 | 이후 매월 계약 시작일의 일자 기준 | `monthly` |
| 재계약 전 | 계약 종료일 **전 마지막 월간 예정일**. 해당 월간을 재계약 회차로 대체 | `monthly-renewal` |

- 발송 시작 시각은 **한국 시간 오후 2시**, 주말·공휴일도 같습니다.
- 실행이 늦어졌다면 **같은 날 오후 6시 정각까지** 새 발송을 허용합니다. 정확한 수신 시각은 실행 지연과 NHN 전달 시간에 따라 달라질 수 있습니다.
- 그 이후 남은 미발송 일정은 다음 관리 실행에서 `PAST_DUE_REVIEW`로 보류합니다. 다음 날 자동으로 몰아서 보내지 않습니다.
- 종료일 당일과 이후에는 새 정기 회차를 만들지 않습니다.
- 종료 30일 전에 별도 메시지를 추가 발송하지 않습니다.
- 실제 실행은 자동 호출 장치가 담당합니다. 날짜 계산 코드만으로 오후 2시에 스스로 실행되지는 않습니다.

### 1-3. 날짜 계산 예시

아래는 **처음부터 발송 대상 조건을 충족하고, 예시의 첫 회차 전에 일정 생성이 시작됐다는 가정**입니다. 중간에 처음 연동한 고객에게 지난 회차를 소급 생성하지 않습니다.

**예시 A — 신규 계약 2026-02-18 ~ 2027-02-18**

| 날짜 | 회차 |
| --- | --- |
| 2026-02-25 | 입주 1주차 |
| 2026-03-18 | 첫 달 |
| 2026-04-18 ~ 2026-12-18, 매월 18일 | 월간 |
| 2027-01-18 | 재계약 전 |
| 2027-02-18 | 계약 종료일이므로 발송 없음 |

**예시 B — 월말 시작 계약**

1월 31일 시작이면 월간 기준일은 2월 28일(윤년은 29일) → 3월 31일 → 4월 30일입니다. 매번 **원래 시작일 31일**을 기준으로 계산하므로, 2월에 28일로 보정됐다고 이후 모든 달이 28일이 되지는 않습니다.

**예시 C — 짧은 계약**

| 계약 | 결과 |
| --- | --- |
| 2026-02-18 ~ 2026-04-01 | 2/25 입주 1주차, 3/18 재계약 전. 유일한 월간이 마지막이므로 첫 달을 대체 |
| 2026-02-18 ~ 2026-03-10 | 2/25 입주 1주차만 생성. 종료 전 월간 날짜가 없음 |
| 2026-02-18 ~ 2026-02-25 | +7일이 종료일과 같으므로 회차 없음 |

**예시 D — 재계약**

재계약으로 확정한 새 계약은 입주 1주차와 첫 달 안내를 다시 보내지 않습니다. 새 계약 시작일 +1개월부터 월간을 만들고, 마지막 월간은 재계약 전 회차로 대체합니다. 재계약 종료 전에 월간 날짜가 하나도 없으면 회차도 없습니다.

### 1-4. 실제 발송 대상 조건

DB에 저장된 고객 중 아래 조건을 충족한 일정만 발송 대상으로 판단합니다.

1. 고객 동기화 상태가 `ready`입니다.
2. 고객상태가 정확히 `계약중` 또는 `입주중`입니다. 앞뒤 공백은 제거하지만 다른 표현을 자동으로 같은 상태로 해석하지 않습니다.
3. 실제 계약이 종료되지 않았고, 저장된 계약 날짜와 최신 고객 날짜가 일치합니다.
4. 계약이 확인 대기 상태가 아니며 연결된 참여자가 활성 상태입니다.
5. 일정이 오늘 날짜의 `planned`이고, 아직 세션·발송 시도가 연결되지 않았습니다.
6. 발송 시간, 템플릿 승인, 환경 설정 및 테스트/운영 모드 조건을 통과합니다.

`매칭중`, `퇴실`, 빈 고객상태 등은 새 발송 대상에서 제외합니다. 날짜 변경으로 계약 확인이 필요한 고객도 보류합니다. 발송 직전에 DB 상태를 다시 확인하지만, **동기화되지 않은 시트 편집까지 알 수는 없습니다.** 당일 연락처 변경·퇴실 등 중요한 수정은 `syncGuests`로 즉시 반영하고 결과를 확인해야 합니다.

### 1-5. 회차별 알림톡 템플릿

아래 코드는 현재 프로그램에 연결된 이름입니다. **문구는 등록·검토용 초안이며 실제 승인 완료를 뜻하지 않습니다.** NHN에서 다른 코드로 등록하면 서버의 회차-템플릿 매핑도 개발자가 맞춰야 합니다.

| 회차 | 템플릿 코드 | 목적 |
| --- | --- | --- |
| 입주 1주차 | `hometo_d7_v1` | 초기 적응과 생활 불편 확인 |
| 첫 달 | `hometo_first_v1` | 첫 달 생활 상태 확인 |
| 월간 | `hometo_monthly_v1` | 정기 생활 상태와 도움 요청 확인 |
| 재계약 전 | `hometo_renewal_v1` | 계약 연장·퇴실 의사 확인 |

**입주 1주차**

```text
[홈투게더] 입주 후 생활 확인

#{name}님, 홈투게더입니다.
입주 후 생활에 불편한 점이 있는지 확인하고자 안내드립니다.
아래 버튼에서 현재 생활 상태와 필요한 도움을 알려주세요.
남겨주신 내용은 운영 담당자가 확인합니다.
```

**첫 달**

```text
[홈투게더] 첫 달 생활 확인

#{name}님, 홈투게더입니다.
입주 첫 달의 생활 상태를 확인하고자 안내드립니다.
아래 버튼에서 생활 중 불편한 점이나 운영 담당자에게 전달할 내용을 알려주세요.
```

**월간**

```text
[홈투게더] 정기 생활 확인

#{name}님, 홈투게더입니다.
계약 기간 중 정기적인 생활 확인을 안내드립니다.
아래 버튼에서 현재 생활 상태와 필요한 도움을 알려주세요.
남겨주신 내용은 운영 담당자가 확인합니다.
```

**재계약 전**

```text
[홈투게더] 계약 종료 전 의사 확인

#{name}님, 홈투게더입니다.
현재 계약 종료를 앞두고 향후 거주 계획을 확인하고자 안내드립니다.
아래 버튼에서 계약 연장 또는 퇴실에 대한 의사와 전달할 내용을 알려주세요.
응답만으로 계약 연장이나 퇴실이 확정되지는 않으며, 담당자가 확인 후 안내드립니다.
```

공통 버튼 이름은 `체크인 응답하기`, 유형은 웹 링크 `WL`입니다. 모바일·PC 링크 모두 운영 도메인의 `/c/#{token}`을 사용합니다. 현재 문서상 주소는 `https://hometogether-checkin-web.vercel.app/c/#{token}`입니다.

- `#{name}`: 해당 고객의 이름으로 치환합니다.
- `#{token}`: 해당 회차에 새로 발급한 비밀 문자열로 치환합니다. 실제 고객 토큰을 템플릿에 고정 입력하지 않습니다.
- 현재 승인 검사 코드는 본문의 변수가 `name`뿐인지, 버튼이 한 개의 `WL`인지, 모바일·PC 주소가 `CHECKIN_APP_ORIGIN`과 일치하는지도 검사합니다. 변수·버튼·도메인을 바꾸면 개발 담당자와 함께 변경해야 합니다.
- 승인 코드 목록에 등록됐다는 설정만 믿지 않고 NHN의 실제 승인 상태(`TSC03`)와 템플릿의 차단·휴면 여부도 확인합니다.
- 문자(SMS) 대체 발송은 현재 요청 코드에서 꺼져 있습니다.

## 2. 알림톡 시스템과 고객 데이터

### 2-1. 고객 데이터는 어디서 오나요?

원본은 Google 스프레드시트 **`홈투게더_고객데이터`의 `게스트_마스터` 탭 하나**입니다. 다른 탭·복사본은 자동으로 연결되지 않습니다. 스크립트가 원본 문서 ID, 탭 ID, 탭 이름을 검사합니다.

고객정보 수정은 원본 시트에서 합니다. 흐름은 **시트 → 우리 서비스 DB 단방향**이며, DB에서 직접 고친 값을 시트로 돌려보내지 않습니다. DB만 고치면 다음 동기화에서 시트 값으로 다시 덮어써질 수 있습니다.

### 2-2. 어느 주기로 DB에 반영되나요?

| 데이터 | 반영 시점 |
| --- | --- |
| 고객정보 | 일일 트리거가 설치돼 있으면 매일 한국 시간 오전 6~7시 사이. `syncGuests` 실행 시 수동 반영 |
| 계약·예정 일정 | 고객 DB의 추가·갱신과 같은 저장 작업 안에서 계산·보류. 별도의 다음 날 배치를 기다리지 않음 |
| 세션·토큰·발송 시도 | 당일 발송 대상 선점 시 생성. 고객 동기화·일정 미리보기 때는 만들지 않음 |
| NHN 접수 결과 | 발송 요청 후 결과를 받으면 반영 |
| 실제 전달 성공·실패 | 서버가 NHN 결과를 다시 조회할 때 반영. 자동 호출 연결 후의 반복 주기에 따름 |
| 설문 응답 | 고객이 최종 제출하고 서버 저장이 성공할 때 반영 |
| 진행·관심 이벤트 | 해당 화면 도달·클릭·선택 완료 이벤트를 서버가 받았을 때 별도 반영 |

시트 편집 즉시 자동 동기화하는 방식은 아닙니다. 6~7시 범위는 코드의 `atHour(6)` 설정에 따른 것으로, Google의 시간 기반 트리거는 지정 시간대 안에서 실행 시각이 정해집니다. 트리거는 만든 계정 권한으로 실행됩니다. [Google 설치형 트리거 안내](https://developers.google.com/apps-script/guides/triggers/installable)

### 2-3. 어떤 필수조건이 있어야 DB에 저장되나요?

**필수 열 제목 8개가 모두 존재해야 하고, 고객별 필수 값 5개가 유효해야 합니다.** 열 제목과 셀 값의 필수 여부를 구분하세요.

| 원본 열 제목 | 고객별 값 필수 | 입력 규칙·주의점 |
| --- | --- | --- |
| `게스트ID*` | 필수 | 대문자 `G` + 숫자 3자리 이상. 예: `G001`. 실제 고객 행 사이에 중복 금지 |
| `이름*` | 필수 | 빈 값 불가 |
| `연락처` | 필수 | 공백·하이픈 제거 후 0으로 시작하는 9~11자리 숫자 |
| `성별` | 선택 | 비워두면 `null` |
| `학교또는직장명` | 선택 | 입력값 그대로 저장. 학교와 직장을 자동 분류하지 않음 |
| `고객상태*` | 저장에는 선택 | 빈 값도 저장 가능하지만 발송은 `계약중`·`입주중`만 가능 |
| `실제 계약 시작일` | 필수 | 유효한 날짜 |
| `실제 계약 종료일` | 필수 | 시작일보다 뒤인 유효한 날짜 |

열 위치는 바꿀 수 있지만 제목의 변경·중복은 허용하지 않습니다. `*`는 현재 열 제목의 일부입니다. 이름을 임의로 바꾸지 마세요.

날짜 셀은 스크립트가 시트 시간대 기준 `YYYY-MM-DD`로 변환합니다. 텍스트로 입력한다면 `2026-09-19`처럼 작성합니다. 연락처는 일반 텍스트로 입력하여 앞자리 `0`을 보존하세요. 이미 사라진 `0`을 시스템이 추측해 복구하지 않습니다.

| 상황 | 결과 |
| --- | --- |
| 신규 고객의 필수 값 완성 | 새 고객 UUID를 만들고 저장 |
| 신규 고객의 필수 값 누락·오류 | 새 고객 저장 제외. 수정 후 다음 동기화에서 재판단 |
| 기존 고객의 필수 값 누락·오류 | 마지막 유효 고객정보·이력을 유지하고 `incomplete`로 보류 |
| 기존 고객 행이 사라짐 또는 선택한 8개 필드 중 ID만 남음 | 삭제하지 않고 `missing`으로 보류 |
| 보류 고객의 정상 정보 복구 | 같은 ID라면 기존 UUID로 갱신, `ready` 복구. 계약·일정 조건은 다시 판단 |
| 정상 행의 성별·학교·상태를 지움 | 해당 값도 DB에서 `null`로 변경 |
| 전체가 빈 데이터·ID만 있는 자리표시자 | 전체 실행 중단. 기존 DB를 통째로 삭제하지 않음 |
| 실제 고객 행의 ID 누락·형식 오류·중복 또는 필수 열 오류 | 전체 실행 중단. 정상 행만 임의로 부분 저장하지 않음 |

### 2-4. DB에 저장되는 고객 데이터

고객 원본 테이블 `checkin_guest`의 업무 데이터는 아래 **8개 항목**입니다.

| 고객정보 | DB 필드 |
| --- | --- |
| 외부 게스트 ID | `guest_id` |
| 이름 | `display_name` |
| 연락처 | `phone` |
| 성별 | `gender` |
| 학교 또는 직장명 | `school` |
| 고객상태 | `customer_status` |
| 실제 계약 시작일 | `contract_start_date` |
| 실제 계약 종료일 | `contract_end_date` |

추가로 내부 UUID, 원본 시트 식별자·행 번호, 생성·변경·동기화 시각, 동기화 상태, 검증 오류 등의 관리 정보가 저장됩니다. 시트의 특이사항·메모·생활패턴·나머지 열 전체는 동기화하지 않습니다.

이는 **고객 시트에서 가져오는 항목의 범위**입니다. 체크인 운영 중 생성되는 계약 스냅샷, 세션, 응답·불만 원문, 진행·관심 이벤트, 발송 결과 등은 별도 테이블에 저장합니다. 시트 특이사항을 저장하지 않는 것과 고객이 설문에 작성한 불만 내용을 저장하는 것은 다릅니다.

### 2-5. 고객 DB를 업데이트하는 방법

일상적인 수정은 다음 순서로 진행합니다.

1. 원본 시트 `게스트_마스터`에서 고객정보를 수정합니다. 고객 ID는 그대로 유지합니다.
2. 시트의 **확장 프로그램 → Apps Script**를 엽니다.
3. 함수 선택에서 **`previewGuests` → 실행**으로 입력의 완성·미완성 건수를 확인합니다. 저장하지 않습니다.
4. 문제가 없다면 **`syncGuests` → 실행**합니다. 이름 끝에 **s가 있는 복수형**입니다.
5. 실행 로그의 건수를 읽고 `held_existing`, `missing_existing`이 있으면 해당 고객 상태를 확인합니다.
6. 권한 있는 담당자가 DB의 `checkin_guest` 및 `checkin_guest_sync_run`에서 반영 여부와 최근 성공 시각을 확인합니다. 계약 날짜를 바꿨다면 일정 보류 여부도 확인합니다.

메뉴가 설치돼 있으면 시트의 **고객 동기화 → 저장 없이 확인 / 지금 동기화**로도 실행할 수 있습니다. 최초 연결이 없으면 담당 계정으로 `configureGuestSync`를 실행해 서버와 같은 동기화 인증값을 설정합니다. 인증값을 시트 셀·코드·공유 문서에 적지 않습니다.

| 함수 | 언제 쓰는가 | 영향 |
| --- | --- | --- |
| `previewGuests` | 저장 전 입력 검사 | DB 저장·발송 없음. 실제 고객별 DB 변경 예상 건수나 발송 대상 수까지 계산하는 함수는 아님 |
| `syncGuests` | 지금 고객정보 반영 | 원본 전체를 검증하고 고객 DB·계약 일정을 반영. 특정 선택 행만 반영하지 않음 |
| `configureGuestSync` | 최초 설정·인증값 교체 | 실행 계정의 연결 인증값 저장 |
| `installDailyGuestSync` | 일일 자동 동기화 설치 | 한 번 저장 성공 후 실행. 미리보기 검사 후 현재 계정의 동명 트리거를 정리하고 하루 한 번 설치 |
| `removeDailyGuestSync` | 자동 동기화 중지·담당자 교체 | 현재 계정이 만든 `syncGuests` 트리거 제거. DB 고객 삭제 없음 |
| `clearGuestSyncConfig` | 해당 계정 연결 해제 | 해당 계정 트리거·인증 설정·최근 성공 기록 제거. DB 고객 삭제 없음 |
| `addGuestSyncMenu` | 시트에 실행 메뉴 표시 | 메뉴만 추가. 고객 동기화는 실행하지 않음 |

일일 트리거는 담당자 **한 계정**에서 관리하세요. 다른 계정이 만든 트리거는 현재 계정에서 보거나 지울 수 없습니다. 담당자 변경 시 이전 계정에서 제거하고 새 계정으로 설정·수동 성공 확인·트리거 설치를 진행합니다. [Google 트리거 권한 설명](https://developers.google.com/apps-script/guides/triggers/installable)

서버 내부의 `sync_checkin_guests`는 DB 저장 함수(RPC)입니다. 관리자가 매일 직접 실행하는 함수는 Apps Script의 `syncGuests`입니다. 옛 서비스 계정 기반 서버 함수·CLI와 혼동하지 마세요.

### 2-6. `previewGuests` 결과 키워드

| 키워드 | 뜻 |
| --- | --- |
| `complete` | 이번에 읽은 실제 고객 행 중 필수 값 검증을 통과한 수. 발송 대상 수가 아님 |
| `incomplete` | 필수 값 검증을 통과하지 못한 실제 고객 행 수 |
| `skippedRows` | 선택한 8개 필드 중 ID만 있고 나머지가 비어 있는 자리표시자 행 수. 완전 빈 행은 이 수에도 포함하지 않음 |

### 2-7. `syncGuests` 결과 키워드

| 키워드 | 정확한 뜻 | 해석·조치 |
| --- | --- | --- |
| `seen` | 이번에 검사·반영 대상으로 보낸 실제 고객 행 수 | 완전 빈 행·ID만 있는 자리표시자는 제외. 신규와 기존 모두 포함 |
| `inserted` | 이번에 새로 저장한 완성 고객 수 | 새 내부 UUID 발급 |
| `updated` | 기존 고객의 업무 값·원본 행 번호·동기화 상태 중 변경이 있었던 완성 고객 수 | 이름·전화번호 수정, 행 이동, 보류 복구 등도 포함 |
| `unchanged` | 비교 대상 값이 동일한 기존 완성 고객 수 | 실패가 아님. 이번 확인·동기화 시각은 갱신되며 일정 재검토도 실행됨 |
| `excluded_incomplete` | 필수 값 오류로 정상 고객정보 반영에서 제외한 행 수 | **신규 고객과 기존 고객 모두 포함** |
| `held_existing` | 위 미완성 행 중 기존 DB 고객이어서 `incomplete`로 처리한 수 | `excluded_incomplete`에 포함되는 수. 둘을 별도 인원처럼 더하지 않음. 이미 보류된 고객도 포함 가능 |
| `missing_existing` | 이번 처리 후 DB에서 `missing` 상태인 고객 전체 수 | **이번에 새로 사라진 수만이 아님.** 이전부터 누락된 고객도 포함 |
| `skipped_placeholders` | ID만 있고 선택한 나머지 7개 필드가 비어 있어 제외한 행 수 | 미리보기의 `skippedRows`에 대응. 미리 만들어 둔 빈 고객 칸이면 정상 |

현재 구현에서 `seen = inserted + updated + unchanged + excluded_incomplete`입니다. `held_existing`은 미완성 수의 부분집합이고, `missing_existing`·`skipped_placeholders`는 별도 범위이므로 모든 값을 합쳐 고객 수로 계산하지 않습니다.

**가상 예시**

```json
{
  "seen": 7,
  "inserted": 1,
  "updated": 2,
  "unchanged": 2,
  "excluded_incomplete": 2,
  "held_existing": 1,
  "missing_existing": 1,
  "skipped_placeholders": 20
}
```

실제 고객 행 7개 중 1명 신규 저장, 2명 변경, 2명 변경 없음, 2명 미완성입니다. 미완성 2명 중 1명은 기존 고객이라 보류됐고 나머지 1명은 신규 저장에서 제외됐습니다. 별도로 DB에 현재 누락 상태 고객이 1명 있으며, ID만 적힌 빈 고객 칸 20개는 건너뛰었습니다.

**`SYNC_SAVED_REVIEW_REQUIRED`가 나왔을 때**

DB 저장은 이미 끝났지만 기존 고객의 미완성·누락을 확인해야 한다는 신호입니다. Google 실행 화면에서 오류처럼 보일 수 있어도 전체 저장 실패로 해석하지 마세요. 스크립트는 마지막 성공 시각과 건수를 저장한 뒤 이 신호를 냅니다. 시트·DB 상태를 확인하고 잘못된 값을 수정한 뒤 다시 동기화합니다.

### 2-8. 자주 보는 오류와 상태

| 코드·상태 | 의미와 조치 |
| --- | --- |
| `ready` / `incomplete` / `missing` | 각각 고객정보 완성 / 기존 필수정보 오류 / 기존 원본 행 누락. `ready`도 발송 승인을 뜻하지 않음 |
| `CONFIGURE_FIRST` / `INVALID_SECRET` | 실행 계정의 연결 설정 없음 / 설정 인증값이 너무 짧음. 담당 계정과 인증값 확인 |
| `UNAUTHORIZED` | 서버 인증 실패. Apps Script와 서버의 인증 설정 일치 여부를 개발 담당자와 확인 |
| `GUEST_SYNC_DISABLED` | 서버 동기화 스위치가 꺼져 있음 |
| `SYNC_ALREADY_RUNNING` | 다른 동기화가 실행 중. 먼저 기존 실행 결과 확인 |
| `INVALID_HEADERS` | 필수 열 이름 누락·중복. 열 제목 확인 |
| `INVALID_OR_DUPLICATE_GUEST_ID` | 실제 고객 행의 ID 오류·중복. 임의 새 ID를 발급하지 말고 원본 확인 |
| `EMPTY_SNAPSHOT` | 실제 고객 행이 하나도 없음. 빈 데이터로 기존 고객 전체를 변경하지 않도록 중단 |
| `SOURCE_HAS_FORMULA_ERROR` | 선택한 8개 열에 수식 오류. 원본 셀 수정 |
| `WRONG_SOURCE` / `SOURCE_TAB_CHANGED` | 원본 문서·탭이 다르거나 탭 이름이 달라짐 |
| `HOST_NOT_ALLOWED` | 설정된 서버 주소가 고정 허용 주소와 다름 |
| `SOURCE_BOUNDS_CHANGED` / `PAYLOAD_TOO_LARGE` | 행·열·요청 크기 제한 초과. 개발 담당자 확인 |
| `STALE_SNAPSHOT` | 읽은 시각이 너무 오래됐거나 미래 시각. 새로 읽어 실행 |
| `GUEST_DATABASE_SYNC_FAILED` / `GUEST_SYNC_FAILED` | DB 반영·서버 처리 실패. 원인은 서버에서 추가 확인 |
| `GUEST_SYNC_NETWORK_FAILED` / `INVALID_SERVER_RESPONSE` | 네트워크 실패 / 정상 건수 응답을 받지 못함. DB 저장 여부를 단정하지 말고 마지막 성공 기록과 비교 |
| `SYNC_ONCE_BEFORE_INSTALL` | 일일 트리거 설치 전에 해당 계정의 수동 저장 성공 필요 |

`GUEST_SYNC_HTTP_503:GUEST_SYNC_DISABLED`처럼 HTTP 상태와 상세 코드가 함께 나올 수 있습니다. 연락처·토큰·인증값 대신 **실행 시각, 오류 코드, 집계 건수**를 개발 담당자에게 전달하세요.

네트워크 오류·429·일부 5xx는 동일 실행 ID·동일 데이터를 사용해 최대 3회 요청합니다. 이 방식은 중복 저장을 막기 위한 것입니다. **고객 동기화의 재시도와 알림톡 재발송 정책은 다릅니다.**

### 2-9. 고객 고유 ID와 토큰의 관계

고객에게는 고유 ID가 있습니다. 다만 용도가 서로 다른 여러 ID를 사용합니다.

| 구분 | 역할 |
| --- | --- |
| 시트 `게스트ID*` → `checkin_guest.guest_id` | 원본 고객을 찾는 업무 ID. 예: `G001` |
| `checkin_guest.id` | DB가 최초 저장 시 발급하는 내부 고객 UUID. 같은 게스트 ID의 정상 갱신에서는 유지 |
| `checkin_contract.id` | 계약 날짜 스냅샷의 ID |
| `logical_contract_id` | 날짜 정정 전후의 같은 계약을 묶는 ID. 재계약은 새 ID |
| `checkin_participant.id` | 당시 고객 이름·전화번호·계약 날짜를 보존하는 참여자 ID |
| `checkin_session.id` | 특정 계약·회차의 응답 기회 ID |
| `checkin_access_token.id` | 토큰 관리 레코드 ID. 고객에게 보내는 토큰 문자열과 다름 |
| 링크의 토큰 문자열 | 그 세션에 접근하기 위한 무작위 비밀값 |

```text
게스트 ID → 내부 고객 UUID → 계약·참여자 → 일정·세션 → 응답
                                                   ↑
                                     토큰 해시로 세션 조회
```

이름·전화번호로 고객을 추측해서 연결하지 않습니다. 전화번호가 바뀌어도 게스트 ID가 같으면 같은 고객 UUID를 유지합니다. 재계약의 과거 응답도 고객 UUID로 연결합니다. 기존에 고객 UUID가 연결되지 않은 과거 참여자는 참여자 ID 기준으로 조회합니다.

**게스트 ID를 바꾸면 다른 고객으로 인식합니다.** 기존 고객은 원본에서 사라진 것으로 보류될 수 있고, 새 ID는 별도 고객으로 저장됩니다. 오타 수정이나 중복 정리를 이유로 ID를 변경해야 한다면 개발 담당자에게 연결 관계 확인을 요청하세요.

고객 ID·전화번호·계약 날짜를 토큰 문자열에 넣지 않습니다. 토큰에서 고객 ID를 읽거나, `G001`을 안다는 이유로 토큰을 만들어낼 수는 없습니다. 서버가 DB 연결 관계로 해당 고객과 회차를 찾습니다.

### 2-10. 토큰 발급·사용·만료

1. 당일 발송 후보의 템플릿·번호·발송 조건을 확인합니다.
2. 서버가 암호학적 난수 32바이트(256비트)를 생성해 URL에 사용할 수 있는 **43자 문자열**로 바꿉니다.
3. DB가 같은 일정에 다른 발송 시도가 없는지 확인하고, 세션·토큰 관리 정보·발송 시도를 한 번에 연결합니다.
4. DB에는 토큰 원문 대신 **SHA-256 해시**를 저장합니다. 원문은 NHN 템플릿의 링크 변수로 전달합니다.
5. NHN 접수만 된 동안은 `delivery_pending`으로 접근을 막습니다.
6. 실제 전달 성공 결과를 DB에 반영하면 링크가 활성화됩니다. 만료 시각은 **NHN의 실제 전달 성공 시각 + 정확히 14일**입니다.
7. 고객이 링크를 열면 서버가 토큰을 검사하고 해당 세션에만 사용할 수 있는 서명된 브라우저 쿠키를 발급합니다. 이후 API 요청에서도 토큰 철회·세션·참여자 상태를 다시 확인합니다.

예를 들어 9월 19일 14:03에 실제 전달됐다면 10월 3일 14:03에 만료됩니다. 고객이 9월 25일 처음 열어도 마감이 뒤로 밀리지 않습니다. 결과를 14:10에 조회했어도 14:03을 기준으로 계산합니다.

전달 직후 아직 서버가 결과를 조회하지 않았다면 링크에 **“일시적인 문제가 생겼어요”**가 표시될 수 있습니다. 반복 결과 조회가 운영에 꼭 필요한 이유입니다. 실제 전달 시각이 누락되거나 잘못된 결과는 자동으로 링크를 활성화하지 않습니다.

| 토큰에 관한 질문 | 현재 동작 |
| --- | --- |
| 고객 한 명이 평생 같은 토큰을 쓰나요? | 아니요. 발송 회차마다 별도 토큰·세션을 사용합니다 |
| 동기화를 실행하면 토큰도 바뀌나요? | 아니요. 동기화는 토큰을 만들거나 교체하지 않습니다 |
| 링크를 한 번 열면 소모되나요? | 아니요. 유효 기간과 상태 조건을 충족하면 같은 링크로 다시 접근할 수 있습니다 |
| 한 번 제출한 뒤 또 제출할 수 있나요? | 한 세션의 최종 응답은 1개입니다. 유효한 접근 상태에서 동일 내용 재시도는 중복 성공으로 처리하고 다른 내용은 충돌로 거절합니다. 고객의 수정 제출 기능은 없습니다 |
| 제출 후 다시 열면 어떻게 되나요? | 토큰이 유효한 동안 “이번 체크인은 이미 답변해 주셨어요”를 표시합니다. 만료 후에는 기간 만료 안내가 우선할 수 있습니다 |
| 링크를 복사·전달할 수 있나요? | 가능합니다. 복사본도 같은 토큰이므로 **같은 고객·회차**에 접근합니다. 복사해서 새 설문 기회를 만들지는 못합니다 |
| 다른 사람이 복사한 링크로 답할 수 있나요? | 유효 링크를 가진 사람은 접근할 수 있습니다. 현재 휴대폰 본인 인증·카카오 계정 확인·단말 고정은 없습니다. 먼저 제출된 응답이 그 고객 회차에 저장될 수 있습니다 |
| 같은 무작위 토큰이 또 생길 수 있나요? | 수학적으로 확률이 0인 것은 아니지만 256비트 난수라 우연 충돌 가능성은 극히 작습니다. DB의 해시 고유 제약도 중복 저장을 막습니다. 실제 관리 위험은 링크 복사·유출입니다 |
| 토큰을 조금 고치면 다른 고객으로 연결되나요? | 보통 일치하는 해시가 없어 잘못된 링크로 처리됩니다. 고객 ID를 바꾸는 방식으로 다른 토큰을 계산할 수는 없습니다 |
| 만료되면 데이터도 지워지나요? | 아니요. 14일은 응답·접근 기한입니다. 고객·응답·이력의 자동 삭제 기간이 아닙니다. 별도 자동 삭제 정책은 현재 구현돼 있지 않습니다 |
| 계약 변경·퇴실 시 기존 링크는 어떻게 되나요? | 동기화·계약 정리 과정에서 참여자가 비활성화되면 기존 링크도 접근이 막힙니다. 과거 응답 데이터는 보존합니다. 상태 복구로 같은 참여자가 다시 활성화되면, 철회되지 않고 기한이 남은 링크는 다시 접근할 수 있습니다 |
| 발송 실패·취소 시에는요? | 결과 반영 시 세션 취소 및 토큰 철회로 접근을 막습니다 |
| 관리자 화면에서 토큰을 재발급하거나 기한을 늘릴 수 있나요? | 현재 그런 UI·운영 절차는 없습니다. 개발 담당자가 기존 발송·응답을 확인하고 별도 처리해야 합니다 |
| DB에서 원래 링크를 다시 찾을 수 있나요? | 우리 DB에는 해시만 있어 원문 복원·복사 기능이 없습니다. 기존 알림톡에 남은 링크와는 별개입니다 |

토큰을 다시 열거나 전달 결과를 반복 조회해도 기한이 연장되지 않습니다. 고객에게 “처음 연 날부터 14일” 또는 “다시 보내면 14일 추가”라고 안내하면 안 됩니다.

쿠키는 브라우저 스크립트가 읽지 못하는 `HttpOnly`, 운영 HTTPS의 `Secure`, `SameSite=Lax`로 설정되며 API 경로에서 사용합니다. 쿠키도 기한과 서명을 확인합니다. 이것이 링크 공유를 막거나 링크 소유자의 신원을 증명하는 것은 아닙니다.

**일정 상태와 보류 사유**

| 값 | 뜻 |
| --- | --- |

| `CONTRACT_REPLACED` | 정정·재계약으로 이전 미발송 일정 교체 |

**발송 시도 상태**

| 값 | 뜻 | 담당자 대응 |
| --- | --- | --- |
| `sending` | DB에서 시도를 잡았고 요청 처리 중 | 10분이 지나도 이 상태면 다음 관리 실행에서 `unknown`으로 전환 |
| `accepted` | NHN 요청 접수. 전달 결과 대기 | 반복 결과 조회 유지 |
| `sent` | 실제 전달 성공 반영 | 응답 여부는 별도로 확인 |
| `failed` | 요청 거절 또는 전달 실패 | 원인 확인. 자동 재발송 없음 |
| `cancelled` | 전달 결과에서 취소 확인 | 링크 차단. 자동 재발송 없음 |
| `unknown` | 요청 접수 여부가 불확실 | NHN 콘솔에서 발송 시도 ID의 그룹키로 조회. 확인 없이 재발송하지 않음 |

DB 선점과 일정별 고유 제약으로 같은 일정에 시도가 겹치지 않도록 합니다. 네트워크 오류로 결과를 모르더라도 이미 NHN이 받았을 수 있어 자동 재발송하지 않습니다. `unknown`의 접수가 확인되면 개발 담당자가 NHN `requestId`·`recipientSeq`를 기존 시도에 연결하고 정상 결과 조회로 복구합니다.

## 3. 관리자 페이지

### 3-1. 접속과 로그인

운영 도메인 기준 경로는 `/admin/login`이며 로그인 후 `/admin/responses`로 이동합니다. 현재 문서상 [관리자 로그인 주소](https://hometogether-checkin-web.vercel.app/admin/login)를 사용하되, 실제 운영 도메인·배포 및 이메일 로그인 검증을 마친 뒤 담당자에게 배포하세요.

1. 등록된 관리자 이메일을 입력합니다.
2. 받은 로그인 이메일의 링크를 엽니다.
3. 응답 화면에서 업무를 진행합니다.
4. 공용 기기에서는 업무 후 로그아웃합니다.

관리자 이메일은 서버의 허용 목록과 인증 사용자 설정이 필요합니다. 이메일 입력만으로 자동 가입되지 않습니다. Google 시트 편집 권한·NHN 계정 권한·관리자 페이지 로그인 권한은 서로 별개입니다.

### 3-2. 화면 구성

현재 상단 메뉴는 **응답 / 로그아웃**입니다. 통계 코드는 있지만 초기 운영에서는 메뉴를 숨겨 두었습니다.

| 영역 | 내용·읽는 방법 |
| --- | --- |
| 상단 요약 | 선택한 필터 범위의 응답·불만·긴급 건수. 전체 발송 고객 수가 아님 |
| 필터 | 회차, 불만 유무, 확인 여부, 접수 시작일·종료일. 기본 최근 30일 |
| 긴급 경로 진입 · 미제출 | 긴급 경로에 도달했지만 최종 제출하지 않은 진행 기록. 확정 신고와 구분 |
| 응답 목록 | 긴급 → 그 외 불만 → 불만 없음 순. 같은 우선순위에서는 최신 제출순 |
| 응답 상세 | 고객·회차·접수 시각, 불만 분류·상세 선택·자유어 원문 |
| 참여자 정보 | 이름·전화번호·매물·집주인·당시 계약 기간 |
| 확인 상태 | `확인함으로 표시` / `확인 해제`, 현재 확인 시각 |
| 진행 기록·관심 정보 | 질문 흐름·시간·선택과 커뮤니티 관심 기록. 펼쳐서 확인 |
| 과거 응답 이력 | 선택한 응답보다 먼저 접수된 같은 고객의 기록. 펼쳐서 확인 |

- 불만 건수에는 긴급 응답도 포함됩니다. 불만+긴급을 더해 별도 고객 수로 계산하지 않습니다. 같은 고객이 여러 회차에 답하면 응답도 여러 건입니다.
- 기본 기간은 **제출일 기준**입니다. 오래된 응답이 안 보이면 필터 기간을 넓히세요. 날짜·시간은 한국 시간으로 표시합니다.
- `긴급 경로 진입 · 미제출`은 도달일·회차 필터만 적용하고 불만·확인 여부 필터는 적용하지 않습니다. 표시가 없다고 모든 미응답자가 안전하다고 판단하지 않습니다.
- 진행 타임라인은 자유어 원문 대신 글자 수 등을 보여줍니다. 불만 원문은 상세의 불만 내용에서 확인합니다.
- 과거 이력은 현재 선택한 응답보다 이전 기록입니다. 같은 태그가 반복돼도 기존 문제가 해결되지 않았다는 사실을 자동으로 확정하지 않습니다.

### 3-3. 어떻게 관리하면 되나요?

권장 업무 순서는 다음과 같습니다. 아래 확인 주기는 운영 제안이며 자동 알림 기능이 아닙니다.

1. 응답 화면을 새로 불러와 최근 기록을 확인합니다. 현재 자동 실시간 갱신 기능은 없습니다.
2. 긴급 완료 응답과 `긴급 경로 진입 · 미제출`을 우선 확인합니다.
3. `미확인` 필터에서 불만 원문과 과거 이력을 읽고 실제 연락·조치 필요 여부를 판단합니다.
4. 연락할 때는 필요하면 원본 시트·최신 고객 DB의 번호와 대조합니다. 상세의 참여자 정보는 당시 계약 스냅샷일 수 있습니다.
5. 내용을 확인했다면 `확인함으로 표시`를 누르고 저장 성공 문구와 확인 시각을 확인합니다. 상세를 여는 것만으로 확인 처리되지 않습니다.
6. 상담 담당자·조치 내용·후속 연락·해결 여부는 팀의 기존 상담 기록 체계에 별도로 남깁니다.
7. 잘못 확인했다면 `확인 해제`를 누릅니다. 저장 실패가 표시되면 성공 처리됐다고 가정하지 말고 재확인합니다.

**`확인함`은 “내용을 확인했다”는 표시입니다.** 문제 해결 완료·고객에게 연락 완료·후속 조치 완료를 뜻하지 않습니다. 현재 확인 기능은 `reviewed_at`을 관리하며 확인한 관리자 ID나 변경 이력 전체를 남기는 기능은 없습니다.

### 3-4. 현재 관리자 화면에서 할 수 없는 일

| 항목 | 현재 상태·대신 사용하는 곳 |
| --- | --- |
| 고객 8개 항목 전체 조회·편집 | 아직 미연결. 원본 시트·권한 있는 고객 DB 조회 사용 |
| 최신 고객정보를 응답 상세에 모두 자동 표시 | 상세는 참여자 스냅샷 기반. 성별·학교·최신 고객상태 등을 모두 보여주는 화면은 아님 |
| 시트 매물·집주인 표시 | 현재 8개 필드 동기화에 포함되지 않아 `등록된 정보 없음`으로 표시될 수 있음 |
| 발송 예정표·발송 성공/실패 대시보드 | 아직 없음. DB·NHN 콘솔·서버 실행 결과로 확인 |
| 고객 동기화 실행 버튼·상세 동기화 이력 | 아직 없음. Apps Script 사용 |
| 템플릿 수정·발송 활성화·재발송·토큰 재발급 | 아직 없음. NHN 콘솔 또는 개발 담당자 처리 |
| 계약 날짜 변경을 정정/재계약으로 확정하는 버튼 | 아직 없음. 개발 담당자의 계약 처리 CLI 사용 |
| 모든 미응답 고객의 관리 목록 | 현재 응답함은 제출 응답 및 긴급 경로 미제출 중심 |
| 담당자 배정·해결 상태·상담 메모·긴급 별도 알림 | 현재 화면에 연결되지 않음. 팀의 별도 업무 체계 필요 |

“응답을 불러올 수 없습니다”는 조회 실패입니다. 이를 “응답 0건”으로 보고 업무를 종료하지 마세요.

## 4. 알아두면 좋은 운영·기획·개발 사항

### 4-1. 일일 운영 점검 제안

| 시점 | 확인할 내용 |
| --- | --- |
| 오전 동기화 후 | Google 실행 성공 여부, DB 마지막 성공 시각, 미완성·누락 고객 |
| 오후 2시 전 | 당일 신규 계약·퇴실·전화번호 변경 반영, 발송 예정 건수·보류 사유, 템플릿·자동 호출 상태 |
| 발송 후 | NHN 접수와 실제 전달 성공을 구분해 확인. `unknown`·실패·남은 후보 점검 |
| 업무 중 정기 확인 | 응답 화면 새로고침, 긴급·미확인 응답, 별도 조치 기록 |
| 오후 6시 이후 | 보류 처리 및 접수된 메시지의 결과 조회가 계속되는지 확인 |

Apps Script가 서버 응답을 받기 전에 실패한 경우 DB 실행 기록이 없을 수 있습니다. **Google 실행 이력과 DB 마지막 성공 시각을 함께 봅니다.** 트리거 자체가 삭제돼 실행되지 않는 경우를 이 코드가 따로 감지해 주지는 않습니다.

### 4-2. 계약 날짜를 수정하거나 재계약할 때

이미 생성된 계약의 날짜가 달라지면 시스템은 단순 오타 수정인지 새 재계약인지 추측하지 않습니다. 고객정보는 반영하되 계약을 `review_required`, 기존 미발송 일정을 보류합니다.

1. 원본 시트 수정 후 `syncGuests`로 반영합니다.
2. 개발 담당자에게 고객 ID, 기존 날짜·변경 날짜, **정정인지 재계약인지**를 전달합니다.
3. 개발 담당자는 최신 미리보기의 계약 ID·날짜를 대조한 뒤 CLI로 확정합니다.
4. 일정과 보류 해소 여부를 재확인합니다.

정정은 같은 논리 계약 ID를 유지하고, 재계약은 새 논리 계약 ID를 만듭니다. 기존 세션·응답은 덮어쓰지 않습니다. 한 번 확인 대기가 된 계약은 시트 날짜를 원래대로 돌려도 자동 해제되지 않습니다.

재계약 설문의 “연장 희망” 응답만으로 원본 계약 날짜가 갱신되거나 계약이 확정되지 않습니다. 담당자의 계약 확인 및 원본 반영이 필요합니다.

### 4-3. 잘못 발송했거나 링크가 유출됐을 때

- 실고객 링크로 담당자가 대신 설문을 제출하지 마세요. 그 고객의 회차를 사용하게 됩니다.
- 잘못된 번호로 보냈다면 원본 번호를 수정·동기화하고, 개발 담당자에게 해당 발송 시도·세션·토큰 철회를 요청합니다. **번호를 고치는 것만으로 이미 보낸 토큰이 바뀌거나 회수되지는 않습니다.**
- 철회·세션 취소로 앞으로의 접근을 막을 수 있지만 이미 전달된 메시지나 타인이 이미 본 내용을 되돌리지는 못합니다.
- 링크 원문을 채팅방·이슈·PR·로그·화면 캡처에 공개하지 않습니다. 지원 요청에는 고객 ID·회차·발송 시도 ID 등 필요한 식별자만 사용합니다.
- 토큰 만료와 개인정보 보관 기간을 구분하고, 고객·응답 데이터의 보관·삭제 정책은 운영 전에 별도로 정해야 합니다.

### 4-4. 중지와 재개를 구분하세요

| 조치 | 영향 |
| --- | --- |
| 고객 동기화 트리거 제거 | 고객 자동 갱신 중지. 별도로 연결된 발송 호출까지 멈추지는 않음 |
| `CHECKIN_GUEST_SYNC_ENABLED=false` 반영 | 고객 동기화 요청 거절. 발송 중지 스위치가 아님 |
| `CHECKIN_DISPATCH_MODE=disabled` 반영 | 새 발송·발송 유지 관리·전달 결과 조회 모두 중지 |
| `CHECKIN_DISPATCH_MODE=dry-run` 반영 | 발송 후보 조회만 수행. 발송·DB 변경·NHN 결과 조회 없음 |
| 특정 고객의 상태 변경 후 동기화 | 해당 고객의 예정 일정·참여자 상태를 다시 판단. 이미 보낸 메시지를 취소하는 기능은 아님 |

발송 모드를 멈추면 접수 상태 메시지의 결과 반영도 멈춰 이미 수신한 고객의 링크가 대기 상태에 남을 수 있습니다. 사고 대응 시 개발 담당자와 함께 **새 발송 중지와 기존 접수 결과 정리**를 구분해 처리하세요. 현재 모드에는 결과 조회만 계속하는 전용 선택지가 없습니다.

### 4-5. 운영 자동 발송 연결 전 완료할 일

1. NHN 네 가지 템플릿의 실제 승인·발신프로필·치환 변수·모바일/PC 링크를 확인합니다.
2. 테스트 DB의 가상 고객과 허용된 담당자 번호로 **요청 접수 → 실제 수신 → 결과 반영 → 링크 진입 → 설문 제출 → 관리자 조회**를 확인합니다. 실고객 번호를 테스트용으로 바꾸지 않습니다.
3. 이번 발송 DB 마이그레이션을 운영에 적용하고 `disabled` 또는 `dry-run` 상태로 배포한 뒤 대상·일정 건수를 대조합니다.
4. 운영자 실제 이메일 로그인·확인/해제 저장, 카카오 인앱 브라우저의 제출·재방문을 검증합니다.
5. 승인된 운영 전환 시점에 운영 발송 설정과 자동 호출 장치를 연결합니다.
6. 주말·공휴일의 응답 확인 담당자, 실패·보류 처리 담당자, 연락·조치 기록 방법을 정합니다.

자동 호출은 오후 2시에 시작하고 이후 결과를 반복 조회할 수 있어야 합니다. **현재 호출 한 번당 새 발송 시도 최대 3건, 기존 접수 결과 조회 최대 3건**입니다. 한 번 실행한다고 그날 고객 전체가 발송 완료되지는 않습니다. 고객 수에 맞춰 호출 간격·처리량을 설계해야 하며 정확한 반복 주기는 아직 확정·연결되지 않았습니다.

리마인더, 실패 자동 재발송, 응답 기한 연장, 이벤트성 수동 알림톡의 자동 운영은 현재 연결돼 있지 않습니다. DB에 관련 구조가 일부 있더라도 실제 운영 기능으로 안내하지 않습니다.

### 4-6. 개발 담당자용 빠른 참고

운영 담당자는 앞의 Apps Script 절차를 사용하고, 아래 명령은 환경 설정을 가진 개발 담당자가 사용합니다. 문서 작성 과정에서 아래 DB·발송 명령을 실행하지 않았습니다.

**날짜 계산만 확인 — DB 접속·발송 없음**

```powershell
pnpm checkin:preview-contract --start=2026-02-18 --end=2027-02-18 --from=2026-02-18
```

**저장된 운영 고객 기준 일정 미리보기 — 기본 DB 변경 롤백, 발송 없음**

```powershell
pnpm checkin:plan-schedules --env=.env.local --expect-project=rfwxpqekweizestlxomi
```

환경 파일이 운영 프로젝트와 일치해야 합니다. 상세 결과는 git에서 제외되는 `artifacts/private` 아래 파일에 기록되므로 공개 첨부하지 않습니다. `--apply`는 실제 저장이고 `--resolution`은 계약 변경 확정 입력이므로 미리보기와 구분합니다. 정확한 입력 형식은 [계약 일정 안내](contract-checkin-schedule.md)를 따릅니다.

**내부 호출 경로와 모드**

- 고객 동기화: `POST /api/integrations/guest-sheet`, `CHECKIN_GUEST_SYNC_SECRET` 인증.
- 체크인 발송: `GET /api/internal/checkin-dispatch`, `CRON_SECRET`의 Bearer 인증.
- `test`: 테스트 발송 스위치 및 허용 번호 목록 필요. 실제 메시지가 전달되는 모드입니다.
- `live`: Production 환경·운영 DB 주소·운영 발송 스위치 조건 모두 필요.
- Vercel Preview의 테스트·운영 발송은 차단합니다.
- NHN API 인증키, 고객 동기화 비밀값, 자동 호출 비밀값, 설문 쿠키 서명 비밀값은 서로 용도가 다릅니다. 고객 토큰과도 다릅니다.

**발송 API 집계 값의 범위**

| 값 | 뜻 |
| --- | --- |
| `mode` | 이번 실행 모드 |
| `candidates` | 조회된 오늘의 DB 후보 수. 최대 1,000건, 시간·템플릿·번호 검사 전이며 이번에 모두 발송했다는 뜻이 아님 |
| `accepted` | 이번 실행에서 NHN 요청 접수가 확인된 수 |
| `held` | 이번에 순회한 후보 중 번호·코드·승인 검사 등에서 건너뛴 수. DB 전체 `held` 일정 수가 아니며 DB 상태를 반드시 변경하는 것도 아님 |
| `reconciled` | 이번 결과 조회에서 `sent`를 확인한 수. 실패를 포함한 모든 조회 건수가 아님 |
| `unknown` | 이번 신규 요청의 접수 결과를 알 수 없었던 수. DB 전체 `unknown` 수가 아님 |

`HTTP 200`도 메시지 전달 완료를 뜻하지 않습니다. `CHECKIN_DISPATCH_FAILED`·503이 발생해도 일부 발송이 이미 접수됐을 수 있으므로, 일정 상태를 `planned`로 되돌려 재발송하지 말고 기존 시도를 확인합니다.
